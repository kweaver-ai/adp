# Context Loader (Feature 806350) 逻辑设计文档

## 1. 功能概述

**Context Loader** 是 Agent Retrieval 服务的核心模块，为智能体（Agent）提供基于知识网络（Knowledge Network）的上下文加载能力。该功能解决了 Agent 在面对海量知识数据时"找不到"和"找不准"的核心问题。

本功能包含两个独立的核心子模块：

| 模块名称 | 功能定位 | 核心能力 |
|---------|---------|---------|
| **KnSearch** | 知识网络搜索 | 提供从 Schema 到 Instance 的全链路检索 |
| **KnowledgeRerank** | 知识重排序 | 提供基于 LLM/Vector 的精细化排序过滤 |

### 1.1 应用场景

- **Agent 意图理解**: Agent 接收用户指令后，需确定知识网络中哪些 ObjectType 和 RelationType 与指令相关
- **RAG 检索增强生成**: 在生成回答前，检索具体的实体数据（Nodes）作为背景知识
- **多轮对话优化**: 利用 Session Cache 缓存上下文，加速后续对话的响应
- **Schema 精排**: 对召回的概念进行二次筛选，提升上下文精准度

## 2. KnSearch 模块

### 2.1 功能说明

KnSearch（知识网络搜索）模块实现了一套完整的知识检索流水线，包含以下核心能力：

1. **Schema 召回**: 从全量 Schema 中筛选与查询相关的 ObjectType 和 RelationType
2. **Schema 重排序**: 对召回的 Schema 进行精细化过滤
3. **实例检索**: 根据筛选后的 Schema 检索具体的实例数据
4. **会话缓存**: 缓存 Schema 以加速多轮对话

### 2.3 核心逻辑详解

#### 2.3.1 Schema 召回 (Concept Retrieval)

**目标**: 解决"查什么"的问题，从全量 Schema 中筛选出与用户 Query 相关的类型。

**处理流程**:

1. **获取全量 Schema**: 调用 OntologyManager 获取知识网络下所有的 ObjectType 和 RelationType
2. **构建 Prompt**: 将关系类型格式化为自然语言描述
   ```
   关系类型编号:
   1. 客户 -> 购买（购买行为记录） -> 产品
   2. 产品 -> 属于（产品分类关系） -> 类目
   3. 销售 -> 负责（销售负责关系） -> 客户
   ```
3. **LLM 筛选**: 调用 LLM 选择 Top-K 个最相关的关系路径
4. **解析结果**: 从 LLM 返回的 `[1, 3]` 格式中提取索引，过滤 Schema

**降级策略**: LLM 调用失败时，返回前 TopK 个关系类型

#### 2.3.2 实例检索 (Semantic Retrieval)

**目标**: 解决"怎么查"的问题，根据筛选后的 Schema 检索具体实体数据。

**单关键词场景**:
- 直接调用 OntologyQuery 接口查询每个 ObjectType 下的实例
- 效率最高，无需额外处理

**多关键词场景** (len(keywords) > 1):

#### 2.3.3 会话缓存 (Session Cache)

- **Key 格式**: `session:{session_id}:kn:{kn_id}`
- **Value**: 序列化的 Filtered Schema (ObjectTypes + RelationTypes)
- **TTL**: 默认 5 分钟
- **作用**: 多轮对话中避免重复的 Schema 召回，降低延迟和 Token 消耗

## 3. KnowledgeRerank 模块

### 3.1 功能说明

KnowledgeRerank（知识重排序）模块提供对概念列表的精细化排序能力，支持两种模式：

| 模式 | 适用场景 | 评分特点 |
|------|---------|---------|
| **LLM 模式** (默认) | Schema 精排、概念筛选 | 二值化评分 (0/1) |
| **Vector 模式** | 实例重排、相似度排序 | 连续分数 (0.0~1.0) |

### 3.3 核心逻辑详解

#### 3.3.1 LLM 模式 (默认)

**Prompt 构建策略**:

```
{{if .Intent}}用户的意图是：{{.Intent}}
{{end}}问题: {{.Question}}
请仔细分析以下概念列表，只返回与上述问题相关的概念编号。
对于与问题无关的概念，请完全忽略，不要在输出中包含它们。
请按照与问题相关性从高到低的顺序返回概念编号。
概念列表:
[1] 我们有一个'客户'的概念，描述为企业客户信息，具有客户名称，联系方式。
[2] 我们有一个'产品'的概念，描述为产品信息表。
[3] 我们有一个'日志'的概念，描述为系统操作日志。
请只返回与问题相关的概念编号，按照相关性排序，以列表形式返回，例如：[3, 1, 5]，都不相关，返回[]
```

**分批处理 (Batching)**:
- 批次大小: 128
- 避免单次请求 Token 超限
- 各批次独立处理，失败不影响其他批次

**评分逻辑**:
- LLM 返回的索引 → Score = 1.0 (相关)
- 未返回的索引 → Score = 0.0 (不相关)
- 最终按 Score 降序排列，相关概念排在前面

**索引解析**:
- 优先匹配 JSON 数组: `\[([0-9,\s]+)\]` → `[1, 3, 5]`
- 降级匹配所有数字: `\d+` → `1, 3, 5`

#### 3.3.2 Vector 模式

**处理流程**:

1. **概念文本化**: 将每个概念转换为描述文本
   ```
   "我们有一个'客户'的概念，描述为企业客户信息，具有客户名称，联系方式。"
   ```

2. **调用 Rerank 服务**:
   ```json
   {
     "query": "用户问题",
     "documents": ["概念1文本", "概念2文本", ...],
     "model": "reranker"
   }
   ```

3. **评分映射**: 直接使用返回的 `relevance_score` (0.0 ~ 1.0)

4. **排序返回**: 按分数降序排列

### 3.4 异常处理策略

| 异常场景 | 处理方式 |
|---------|---------|
| 概念列表为空 | 直接返回空列表 |
| LLM 批次调用失败 | 跳过该批次，继续处理其他批次 |
| LLM 解析失败 | 该批次概念得分为 0.0 |
| Vector 服务超时 | 降级返回原顺序，所有概念得分为 0.0 |
| 概念格式化失败 | 降级使用概念名称作为文本 |

## 4. 关键配置项

### 4.1 KnSearch 配置

| 配置项 | 说明 | 默认值 |
|-------|------|-------|
| `defaultTopK` | Schema 召回的最大数量 | 10 |
| `maxKeywords` | 多关键词场景的最大关键词数 | 5 |
| `perTypeLimit` | 每个 ObjectType 检索的实例上限 | 10 |
| `scoreRatio` | 实例过滤的相对分数阈值 | 0.25 |
| `sessionCacheTTL` | 会话缓存过期时间 | 300s |

### 4.2 KnowledgeRerank 配置

| 配置项 | 说明 | 默认值 |
|-------|------|-------|
| `batchSize` | LLM 模式的批次大小 | 128 |
| `model` | 使用的 LLM 模型 | 配置文件指定 |
| `temperature` | LLM 采样温度 | 0.0 |
| `maxTokens` | LLM 最大输出 Token | 配置文件指定 |
